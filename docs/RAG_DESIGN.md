# RAG & Knowledge Retrieval System Design

## 1. Architectural Philosophy: The Hybrid SQL + Vector Paradigm

A critical hazard in applying generative AI to hospitality fintech is the tendency of Large Language Models to hallucinate numerical calculations. Asking a vector retrieval index *"What is our collected revenue?"* can return contradictory numbers from stale documents.

To solve this, the platform implements a **Hybrid SQL + Vector Architecture**:
1. **Authoritative Structured Facts:** All numerical calculations (Booked Revenue, Invoiced Revenue, Collected Revenue, Accounts Receivable, ADR, RevPAR, Occupancy %, Z-Scores) are executed deterministically via SQL over the PostgreSQL/SQLite database.
2. **Contextual Semantic Documents:** Unstructured operational briefs, historical reports, competitor amenity profiles, and audit alert messages are indexed into vector embeddings for semantic retrieval.
3. **Evidence-Grounded Synthesis:** The `/ask` and `/bde/ask` endpoints query both layers: structured metrics provide the exact numbers, while retrieved vector documents provide the qualitative context, citations, and operational recommendations.

```
+----------------------------------------------------------------------------------+
|                            USER QUESTION (/ask endpoint)                         |
+----------------------------------------------------------------------------------+
                                        │
             ┌──────────────────────────┴──────────────────────────┐
             ▼                                                     ▼
+──────────────────────────+                              +──────────────────────────+
| DETERMINISTIC SQL ROUTER |                              | SEMANTIC VECTOR ROUTER   |
| (Numerical Inquiries)    |                              | (Context & Competitors)  |
+──────────────────────────+                              +──────────────────────────+
             │                                                     │
             ▼                                                     ▼
   Authoritative Ledger                                   Qdrant / In-Memory Index

             │                                                     │
             └──────────────────────────┬──────────────────────────┘
                                        │
                                        ▼
+----------------------------------------------------------------------------------+
|                    EVIDENCE-GROUNDED RESPONSE SYNTHESIZER                        |
|  - Exact deterministic numbers from PostgreSQL                                   |
|  - Qualitative operational context from indexed reports                          |
|  - Explicit citations, confidence levels, and data limitation disclaimers       |
+----------------------------------------------------------------------------------+
```

## 2. Document Extraction & Metadata Schema

The `RAGDocumentLoader` (`rag/document_loader.py`) indexes three core document types:

1. **Formal Operational Reports:** Generated by the `ReportingAgent` (`DAILY_OPERATIONS`, `REVENUE_ANALYSIS`, `RECONCILIATION_EXCEPTION`).
2. **Competitor Intelligence Profiles:** Generated by the `BDEAgent`, cataloging competitor names, star ratings, proximity distances, and verified amenities.
3. **Operational Alerts:** Actionable flags raised by the reconciliation and expense audit engines.

### Metadata Schema:
```json
{
  "doc_type": "report | competitor_profile | alert",
  "property_id": "BER | LND | MUC | PAR | VIE | ALL",
  "created_at": "2026-10-11T12:00:00Z",
  "source": "ReportingAgent | BDEAgent | OperationsMonitor"
}
```

## 3. Vector Embeddings & Offline Zero-Dependency Fallback

The `EmbeddingsService` (`rag/embeddings.py`) supports dual execution modes:
- **Production Mode:** When `OPENAI_API_KEY` is present, uses `text-embedding-3-small` (1536 dimensions) for high-dimensional semantic search.
- **Local / Evaluation Fallback Mode:** When no external API key is configured, uses a deterministic dense hash-vector embedder (128 dimensions) with L2 normalization. This ensures all semantic search tests pass offline with zero external network dependencies and zero financial cost.
